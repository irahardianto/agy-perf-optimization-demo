# FlashMart API

Storefront API behind the FlashMart web and mobile apps: **catalog search**, **product
details** and **cart pricing** (promotions, live stock, shipping and loyalty discounts).

The **11.11 mega sale** is coming and marketing projects roughly **10× normal traffic**. The
[11.11 readiness targets](#1111-readiness-targets) below are what the service has to sustain.
As of v1.4.0 it does not meet them yet.

- Plain Node.js (ESM JavaScript). **No dependencies**, no build step, no database, no Docker.
- Runs fully offline. Data is generated locally and deterministically.
- Requires Node.js **18.18+** (20 or 22 LTS recommended).

---

## Quick start

```bash
npm run setup     # generate data/ (12,000 products, 300 promotions, API keys) — offline, ~2 s
npm start         # http://127.0.0.1:3000
npm test          # unit + HTTP tests (~1 s)
npm run doctor    # pre-flight check of this machine (Node, git, data, speed, tests, server)
```

Every npm script is a thin wrapper around `node`, so you can always call the file directly:

| npm script | Direct equivalent | What it does |
|---|---|---|
| `npm run setup` | `node scripts/seed.mjs` | Generates `data/` (skips if already generated; `--force` to regenerate) |
| `npm start` | `node src/server.js` | Starts the API |
| `npm test` | `node scripts/test.mjs` | Runs the test suite (Node's built-in test runner) |
| `npm run check` | `node scripts/check.mjs` | Syntax check of every JS file + basic hygiene rules |
| `npm run bench` | `node bench/run.mjs` | Load benchmark against the 11.11 targets |
| `npm run bench:quick` | `node bench/run.mjs --quick` | Shorter benchmark for fast feedback |
| `npm run bench:compare` | `node bench/compare.mjs` | Compares two saved benchmark runs |
| `npm run profile` | `node tools/perf/profile.mjs` | CPU + allocation profile under load, with a text summary |
| `npm run doctor` | `node scripts/doctor.mjs` | Environment pre-flight check |
| `npm run reset -- --yes` | `node scripts/reset.mjs --yes` | Restores the repo to the `baseline` tag (discards later commits and generated reports) |

> **Windows / PowerShell:** if `npm` fails with *"running scripts is disabled on this system"*,
> use `npm.cmd` instead (`npm.cmd run bench`) or call `node` directly as shown above. In Windows
> PowerShell 5.1, `curl` is an alias for `Invoke-WebRequest` — use `curl.exe` for the examples below.

## Architecture

```
src/
  server.js                 process entry point: HTTP server, graceful shutdown
  app.js                    wiring: routing, auth, error handling, request history
  config.js                 environment configuration
  http/                     minimal router + JSON request/response helpers
  auth/                     API key store + authenticator (SEC-112)
  catalog/                  catalog snapshot repository, search, catalog routes
  pricing/                  cart validation, promotions, cart pricer, pricing routes
  external/                 clients for services owned by other teams (simulated) — do not modify
  internal/                 operator endpoints (metrics, request history, key revocation)
  platform/                 logger, runtime metrics, request history
data/                       generated by `npm run setup` (git-ignored)
bench/                      load benchmark harness + 11.11 targets
tools/perf/                 profiling harness (CPU profile + allocation sampling)
test/                       node:test suites
scripts/                    setup, test runner, checks, doctor, reset
```

**Catalog data.** The merchandising system exports the full catalog (products + promotions) to
`data/catalog.json`. The API serves search, product details and pricing from that snapshot.

**External services.** Stock levels come from the warehouse inventory API, shipping quotes from
the carrier, and customer tiers from the rewards programme. In this repo they are simulated with
production-like latency — see [`src/external/README.md`](src/external/README.md).

## API

All `/api/*` routes require an `x-api-key` header. `/internal/*` routes require
`x-internal-token` (default for local runs: `local-internal-token`).

| Method & path | Description |
|---|---|
| `GET /healthz` | Liveness check (no auth) |
| `GET /api/products/search` | Full-text search with filters, sorting and pagination |
| `GET /api/products/:sku` | Product details plus currently active deals |
| `POST /api/cart/price` | Prices a cart |
| `GET /internal/metrics` | Request counters, event-loop delay and memory. `?gc=1` forces a GC first (only with `--expose-gc`), `?reset=1` resets counters after reading |
| `GET /internal/requests?limit=50` | The most recent API requests, newest first (`limit` 1–200), used by the support team to see what a client actually sent |
| `POST /internal/keys/:id/revoke` | Revokes an API key |

### Search parameters

| Parameter | Default | Notes |
|---|---|---|
| `q` | *(empty)* | Up to 100 characters. Matches name (weight 3), brand (2), tags (1), description (0.5) |
| `category` | — | Exact category match, e.g. `audio`, `laptops`, `kitchen` |
| `minPrice`, `maxPrice` | — | Integer cents |
| `sort` | `relevance` | `relevance` · `price_asc` · `price_desc` · `rating` (empty `q` + `relevance` sorts by rating) |
| `limit`, `offset` | `20`, `0` | `limit` 1–50, `offset` 0–10000 |

### Examples

```bash
curl -s "http://127.0.0.1:3000/api/products/search?q=wireless+earbuds&limit=3" \
  -H "x-api-key: fmk_web01.Vt8q2KfN4xLm7RcZ"

curl -s "http://127.0.0.1:3000/api/products/FM-000042" \
  -H "x-api-key: fmk_web01.Vt8q2KfN4xLm7RcZ"

curl -s -X POST "http://127.0.0.1:3000/api/cart/price" \
  -H "x-api-key: fmk_app01.Hs3wP9dQ6yBn1TgJ" -H "content-type: application/json" \
  -d '{"customerId":"cust-1001","destination":{"country":"ID","postalCode":"10110"},"items":[{"sku":"FM-000042","quantity":2},{"sku":"FM-000777","quantity":1}]}'

curl -s "http://127.0.0.1:3000/internal/metrics" -H "x-internal-token: local-internal-token"
```

Errors always have the same shape (and 401 responses never say *why* a key was rejected):

```json
{ "error": { "code": "invalid_cart", "message": "Cart request is invalid", "requestId": "…", "details": ["…"] } }
```

## Operational requirements

These are product, security and platform commitments. **Any change — including performance
work — must preserve all of them.** Most are covered by the test suite.

1. **Catalog freshness.** The merchandising exporter replaces `data/catalog.json` every few
   minutes by writing a temp file and renaming it over the old one. Price and promotion changes
   must be visible on **every endpoint within 1 second**, without a restart.
2. **API key security (SEC-112).** Secrets are verified against PBKDF2-HMAC-SHA512 hashes using
   the parameters stored with each key record. The KDF, digest, iteration count and key length
   must not be weakened or replaced without security sign-off. A secret that does not match the
   stored hash must never be accepted, and revoking a key must take effect on the **very next
   request**.
3. **Pricing rules.**
   - Each line gets the single best eligible promotion (promotions don't stack); ties go to the
     lowest promotion id.
   - Promotion windows (`startsAt` / `endsAt`) are evaluated at request time — flash deals start
     and end on the minute.
   - Only lines that are in stock are shipped and charged; shipping is quoted on their weight.
   - The loyalty discount applies to the merchandise total after promotions.
4. **API contracts.** Response shapes, status codes and the error format are consumed by the web
   and mobile apps and must not change.
5. **External services.** `src/external/` stands in for systems owned by other teams. Change how
   FlashMart *calls* them, never the clients themselves.
6. **Measurement harness.** `bench/` and `tools/perf/` define how performance is measured.
   Don't modify them while optimizing, so that results stay comparable with the baseline.

## Performance tooling

### Benchmark

```bash
npm run bench                          # all scenarios, 5 s each after warm-up
npm run bench:quick                    # 2 s per scenario
npm run bench -- --scenario cart       # search | product | cart | mixed (comma-separated)
npm run bench -- --label baseline      # save as bench/results/baseline.json
npm run bench -- --count 3 --label final   # repeat each scenario 3×, report the median
npm run bench:compare -- baseline final    # before/after table (label, file path, or "latest")
```

The benchmark starts its own server on a free port, drives each scenario with a fixed number of
concurrent keep-alive connections (default 16), and reports:

| Column | Meaning |
|---|---|
| `req/s` | Completed requests per second during the measured window |
| `p50/p95/p99/max ms` | Client-observed latency percentiles |
| `errors` | Non-2xx responses and transport errors |
| `loop p99 ms` | 99th percentile event-loop delay inside the server: how long ready work waits for the single JS thread |
| `heap MB` | V8 heap still in use after a forced GC at the end of the scenario (scenarios share one server process) |

Scenarios: `search` (keyword and category searches), `product` (product detail pages), `cart`
(2–8 line carts), `mixed` (50% search / 30% product / 20% cart).

### Profiler

```bash
npm run profile                                   # mixed scenario, 8 s under load
npm run profile -- --scenario cart --label cart   # any scenario; output in .profiles/<label>/
```

Writes to `.profiles/<label>/`:

- `summary.md` — text summary: time by category (project code / Node internals / GC / idle),
  project hot spots, **hot source lines**, inclusive time, hot call paths, allocation hot spots,
  and retained memory before/after the load.
- `cpu.cpuprofile` — open in Chrome DevTools (Performance panel → *Load profile*) or VS Code for
  a flame chart.
- `alloc.heapprofile` — sampled allocations; open in Chrome DevTools (Memory panel → *Load*).

The analyzers also work on their own:
`node tools/perf/analyze-cpuprofile.mjs <file.cpuprofile>` and
`node tools/perf/analyze-heapprofile.mjs <file.heapprofile>`.

### 11.11 readiness targets

Measured by `npm run bench` at 16 concurrent connections:

| Scenario | Target |
|---|---|
| search | p95 ≤ 100 ms |
| product | p95 ≤ 50 ms |
| cart | p95 ≤ 150 ms |
| mixed | ≥ 250 req/s and p95 ≤ 150 ms |
| all | event-loop delay p99 ≤ 50 ms, no errors |

```bash
npm test                                         # all suites
npm test -- --test-name-pattern="catalog"        # filter by test name
npm run check                                    # syntax + hygiene checks
```

Tests run with `SIMULATE_EXTERNAL_LATENCY=0` and use a small generated catalog, so the whole
suite finishes in about a second.

## Configuration

| Variable | Default | Description |
|---|---|---|
| `PORT` | `3000` | HTTP port (`0` = random free port) |
| `HOST` | `127.0.0.1` | Bind address |
| `LOG_LEVEL` | `info` | `debug` · `info` · `warn` · `error` |
| `DATA_DIR` | `./data` | Directory with generated data |
| `CATALOG_PATH` | `$DATA_DIR/catalog.json` | Catalog snapshot |
| `API_KEYS_PATH` | `$DATA_DIR/api-keys.json` | API key records |
| `INTERNAL_TOKEN` | `local-internal-token` | Token for `/internal/*` |
| `SIMULATE_EXTERNAL_LATENCY` | `1` | `0` disables simulated external latency |
| `MAX_BODY_BYTES` | `262144` | Maximum JSON request body |

### Slow machine?

`npm run doctor` measures this machine. If it reports a slow machine, generate a smaller catalog
(benchmarks stay comparable as long as before/after runs use the same data):

```bash
node scripts/seed.mjs --products 6000 --promotions 150 --force
```
